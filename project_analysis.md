# 📋 Полный анализ проекта: Telegram Bot для системы документооборота машиностроительного предприятия

## 📌 Общее описание проекта

**Назначение:** Асинхронный Telegram-бот для управления технической документацией машиностроительного предприятия. Позволяет искать, добавлять, фильтровать, скачивать документы (чертежи, техпроцессы, спецификации) через Telegram-интерфейс с возможностью использования локальной LLM (через LM Studio) для интеллектуального поиска и генерации ответов (RAG — Retrieval-Augmented Generation).

**Стек технологий:**
- **Python 3.10+** — язык программирования
- **python-telegram-bot 22.x** — асинхронная работа с Telegram Bot API
- **SQLAlchemy 2.0 (асинхронный)** — ORM для работы с базой данных
- **SQLite (aiosqlite)** — БД по умолчанию, возможна замена на PostgreSQL
- **LM Studio** — локальный LLM-сервер с OpenAI-совместимым API
- **aiohttp** — асинхронные HTTP-запросы к LLM

---

## 🏗️ Общая архитектура (как это работает)

```
Пользователь (Telegram)
        ↓
Telegram Bot API
        ↓
python-telegram-bot (Application)
    ├── Handlers (слой обработки запросов пользователя)
    │   ├── commands.py — обработка команд /start, /search, /find, /add и т.д.
    │   ├── callbacks.py — обработка нажатий inline-кнопок
    │   └── messages.py — обработка произвольных текстовых сообщений
    │
    ├── Services (сервисный слой с бизнес-логикой)
    │   ├── document_service.py — координация поиска, добавления, фильтрации
    │   ├── llm_service.py — взаимодействие с локальной LLM (RAG)
    │   └── file_service.py — работа с файлами (сохранение, чтение, валидация)
    │
    ├── Database (слой данных)
    │   ├── models.py — SQLAlchemy ORM модели (Document, DocumentHistory, User)
    │   ├── repository.py — CRUD-операции + fallback JSON-хранилище
    │   └── init_test_data.sql — тестовые данные для разработки
    │
    └── Utils (утилиты)
        ├── logger.py — логирование (консоль + файл)
        └── validators.py — валидация входных данных
```

**Точка входа:** `main.py` — инициализирует БД, сервисы, настраивает обработчики и запускает polling (опрос серверов Telegram на предмет новых сообщений).

**Data Flow типичного запроса:**
1. Пользователь отправляет сообщение → Telegram → Bot API → python-telegram-bot
2. `Application` определяет тип сообщения: команда, callback, текст, файл, голос
3. Соответствующий `Handler` обрабатывает запрос
4. Handler вызывает методы `DocumentService` (сервисный слой)
5. `DocumentService` обращается к `DocumentDatabase` (репозиторий) или `LLMProcessor`
6. Результат возвращается обратно по цепочке → ответ пользователю

#### `main.py` — Точка входа в приложение (216 строк)
**Зачем:** Запускает бота, инициализирует все компоненты.
**Что делает:**
- Загружает конфигурацию через `Config`
- Создаёт экземпляр `DocumentDatabase` (БД) и инициализирует её
- Создаёт `LLMProcessor` (подключение к LM Studio)
- Создаёт `DocumentService` (бизнес-логика), передавая ему БД и LLM
- Создаёт `Application` (python-telegram-bot) с токеном
- Сохраняет сервисы в `app.bot_data` для доступа из всех обработчиков
- Регистрирует все обработчики (команды, conversation handler, callback-запросы, сообщения)
- Запускает фоновую задачу `schedule_folder_import` — каждые 300 секунд (5 мин) сканирует папку загрузок и импортирует новые файлы
- Запускает polling (опрос Telegram API на предмет новых сообщений)
- Реализует graceful shutdown — корректное закрытие БД, LLM, приложения при остановке

**Почему так:**
- Разделение инициализации и запуска упрощает тестирование и поддержку
- Фоновая задача импорта обеспечивает автоматическую синхронизацию с файловой системой
- Graceful shutdown предотвращает повреждение данных при аварийном завершении

#### `database/models.py` — ORM модели базы данных (109 строк)
**Зачем:** Определяет структуру таблиц в виде Python-классов (SQLAlchemy ORM).
**Содержит 3 модели:**

1. **`Document`** — основная модель документа технической документации:
   - `id` — первичный ключ (автоинкремент)
   - `doc_id` — уникальный идентификатор документа (например, `DOC-2024-001`) с уникальным индексом
   - `title` — название документа (обязательное поле)
   - `doc_type` — тип документа (Чертеж, Техпроцесс, Спецификация, Инструкция, Схема, Расчет)
   - `drawing_number` — номер чертежа по ЕСКД
   - `version` — версия документа
   - `tech_process` — техпроцесс (Токарная, Фрезерная и т.д.)
   - `status` — статус (Активен, Архивный, В работе, Отменен)
   - `file_path` — путь к файлу на диске
   - `file_name` — оригинальное имя файла
   - `tags` — теги через запятую
   - `description` — описание документа
   - `created_at` / `updated_at` — даты создания и обновления
   - `created_by` — кто создал документ
   - `metadata_json` — дополнительные поля в формате JSON
   - `history` — связь с историей изменений (отношение one-to-many)
   - Индексы: `doc_id`, `status`, `tech_process`, `doc_type`
   - Метод `to_dict()` — преобразование модели в словарь

2. **`DocumentHistory`** — история изменений документов:
   - `doc_id` — внешний ключ к `documents.doc_id`
   - `action` — действие (CREATE, UPDATE_STATUS, UPDATE_VERSION, DELETE)
   - `old_value` / `new_value` — старые и новые значения
   - `changed_at` — дата изменения
   - `changed_by` — кто изменил
   - Связь с `Document`

3. **`User`** — модель пользователя для авторизации:
   - `telegram_id` — уникальный Telegram ID
   - `username` — имя в Telegram
   - `full_name` — полное имя
   - `role` — роль (admin, engineer, technologist)
   - `is_active` — активен ли пользователь

**Почему так:**
- Использование ORM (SQLAlchemy) позволяет абстрагироваться от типа БД (SQLite/PostgreSQL)
- Индексы на часто используемых полях ускоряют поиск
- История изменений обеспечивает аудит действий пользователей
- `metadata_json` позволяет хранить произвольные дополнительные поля без изменения схемы БД
- Каскадное удаление (`cascade="all, delete-orphan"`) автоматически удаляет историю при удалении документа

#### `database/repository.py` — Репозиторий для работы с БД (605 строк)
**Зачем:** Реализует паттерн Repository — единый интерфейс доступа к данным с CRUD-операциями и поисковыми методами.
Реализует два режима хранения: основное БД (через SQLAlchemy) и fallback JSON-хранилище для случаев недоступности БД.

**Основные методы:**

**Инициализация:**
- `initialize()` — создаёт асинхронный движок БД, фабрику сессий, создаёт таблицы. При ошибке переключается на JSON-хранилище

**CRUD операции:**
- `add_document(data, file_content, user)` — создаёт новый документ (сохраняет файл на диск, записывает в БД, добавляет запись в историю)
- `get_document_by_id(doc_id)` — получение документа по ID
- `update_document(doc_id, data, user)` — обновление метаданных документа
- `update_status(doc_id, new_status, user)` — изменение статуса с записью в историю
- `delete_document(doc_id, user)` — мягкое удаление (архивирование, а не физическое удаление)
- `get_document_file(doc_id)` — чтение содержимого файла с диска
- `get_all_documents(page, per_page)` — список документов с пагинацией
- `get_total_count()` — общее количество документов
- `get_statistics()` — статистика (общее количество, по типам, статусам, техпроцессам)

**Поиск:**
- `search_by_criteria(filters)` — поиск по нескольким критериям (тип, статус, техпроцесс)
- `fulltext_search(query_text)` — полнотекстовый поиск по названию, описанию, тегам, doc_id, номеру чертежа

**Fallback (JSON-хранилище) — 6 методов:**
- `_load_fallback()` — загрузка данных из `fallback_db.json`
- `_save_fallback()` — сохранение данных в `fallback_db.json`
- `_fallback_search()`, `_fallback_text_search()`, `_fallback_get()`, `_fallback_add()`, `_fallback_update_status()`, `_fallback_stats()` — дублируют функциональность БД для работы с JSON

**Вспомогательные:**
- `_add_history()` — запись в историю изменений
- `_save_file()` — генерация уникального имени файла с датой и временем и сохранение на диск
- `_generate_doc_id()` — генерация ID формата `DOC-ГГГГ-NNNN`
- `close()` — закрытие соединения с БД

**Почему так:**
- Паттерн Repository изолирует работу с БД от остального кода
- Fallback JSON-хранилище обеспечивает отказоустойчивость — бот продолжает работать даже при недоступности БД
- Каждая операция оборачивается в try-except с fallback для максимальной устойчивости
- Асинхронные методы (`async/await`) обеспечивают неблокирующую работу
- Пагинация предотвращает перегрузку при большом количестве документов
- Сохранение файлов с уникальными именами предотвращает коллизии имён

#### `services/document_service.py` — Бизнес-логика работы с документами (345 строк)
**Зачем:** Реализует паттерн Service Layer — координирует работу репозитория, LLM и файлового сервиса.
Содержит основную бизнес-логику приложения.

**Методы:**

**Поиск:**
- `search_documents(query)` — простой полнотекстовый поиск (делегирует репозиторию)
- `smart_search(query)` — "умный" поиск в 2 этапа:
  1. Выполняет SQL-поиск
  2. Если результатов меньше `MIN_SEMANTIC_RESULTS` (2) — использует LLM для генерации синонимов
  3. Выполняет дополнительный поиск по каждому синониму
  4. Объединяет результаты, убирает дубликаты
  5. Определяет наиболее релевантный результат
  6. Возвращает словарь с результатами, синонимами, сообщением

**Фильтрация:**
- `filter_documents(doc_type, status, tech_process)` — фильтрация по одному или нескольким критериям

**Операции с документами:**
- `get_document_info(doc_id)` — получение полной информации о документе (включая размер файла)
- `download_document(doc_id)` — получение файла документа (содержимое + имя)
- `add_new_document(data, file_content, user)` — добавление с валидацией (название не пустое, расширение файла допустимо)
- `change_status(doc_id, new_status, user)` — изменение статуса с проверкой (только допустимые статусы, проверка на дублирование статуса)

**RAG-обработка:**
- `process_free_text(text)` — обработка произвольного текста через LLM с RAG:
  1. Поиск релевантных документов
  2. Если не найдено — запрос синонимов через LLM
  3. Повторный поиск по синонимам
  4. Формирование промпта с контекстом из найденных документов
  5. Отправка в LLM и возврат ответа пользователю

**Утилиты:**
- `get_document_list(page, per_page)` — пагинированный список документов
- `get_statistics()` — статистика архива
- `import_documents_from_folder(folder)` — пакетный импорт файлов из папки (создаёт записи в БД для каждого файла)
- `get_available_types()` / `get_available_statuses()` / `get_available_tech_processes()` — списки доступных значений

**Почему так:**
- Разделение по методам с чёткой ответственностью упрощает тестирование
- Умный поиск с LLM улучшает результаты поиска, когда SQL-поиск даёт мало результатов
- Валидация перед записью в БД предотвращает некорректные данные
- Сервисный слой скрывает от обработчиков детали работы с БД и LLM

#### `services/llm_service.py` — Взаимодействие с локальной LLM (261 строка)
**Зачем:** Реализует RAG (Retrieval-Augmented Generation) — подстановку контекста из найденных документов в промпт для LLM.
Использует LM Studio с OpenAI-совместимым API.

**Класс `LLMProcessor`:**

**Основные методы:**
- `process_query(user_query, context_docs)` — основной метод:
  1. Формирует контекст из найденных документов (макс. 5)
  2. Создаёт system_prompt (роль ассистента) и user_prompt (контекст + вопрос)
  3. Отправляет запрос в LM Studio через API
  4. При ошибке использует `_fallback_response()`

- `suggest_synonyms(query)` — генерация синонимов для улучшения поиска:
  1. Формирует промпт для LLM с просьбой вернуть 3-5 синонимов
  2. Получает ответ, разбивает на строки
  3. Возвращает максимум 5 синонимов
  4. При ошибке возвращает исходный запрос

- `classify_intent(query)` — классификация намерения пользователя:
  1. Возвращает JSON с полями intent (search, filter, add, help, unknown) и params
  2. Используется для понимания, что хочет пользователь по свободному тексту

- `generate_document_summary(doc)` — генерация краткого описания документа (2-3 предложения)

**Вспомогательные методы:**
- `_make_request(messages, max_tokens, temperature)` — отправка HTTP-запроса к LM Studio:
  - Формирует payload в формате OpenAI Chat Completions API
  - Отправляет POST на `{api_url}/chat/completions`
  - Таймаут 120 секунд
  - Обработка ошибок (статус, таймаут, исключение)

- `_fallback_response(query, docs)` — формирование ответа без LLM (при недоступности API):
  - Простое форматирование списка найденных документов
  - Если документов нет — предлагает изменить запрос

- `close()` — закрытие HTTP-сессии

**Почему так:**
- RAG позволяет LLM отвечать на основе актуальных данных из БД, а не только на основе своего обучения
- Fallback-ответ без LLM обеспечивает работоспособность при недоступности LM Studio
- OpenAI-совместимый формат позволяет использовать любую LLM, поддерживающую этот стандарт
- Низкая температура (0.3) делает ответы более точными и предсказуемыми
- Ограничение в 5 документов контекста предотвращает превышение лимита токенов

#### `handlers/messages.py` — Обработчики произвольных сообщений (159 строк)
**Зачем:** Реализует основную "фишку" бота — RAG-обработку произвольных текстовых сообщений.
Пользователь может просто написать вопрос, и бот сам найдёт релевантные документы и ответит.

**Компоненты:**

- `_SEARCH_WORDS` — кортеж ключевых слов, указывающих на поисковый запрос (найди, найти, поиск, покажи, документ, чертёж и т.д.)
- `_SEARCH_HINTS` — кортеж слов, которые в длинных запросах (более 3 слов) указывают на поиск
- `_looks_like_search_request(text)` — эвристический анализ текста:
  1. Если в тексте есть слова из `_SEARCH_WORDS` → поисковый запрос
  2. Если слов 3 или меньше → не поисковый запрос (возможно, это просто название)
  3. Если слов больше 3 и есть слова из `_SEARCH_HINTS` → поисковый запрос

**Обработчики:**

- `handle_message(update, context)` — основной обработчик текстовых сообщений:
  1. Если `_looks_like_search_request()` → поиск через RAG (process_free_text)
  2. Иначе → LLM-ассистент (тоже через process_free_text, но без явного поиска)
  3. При ошибке LLM → fallback: базовый поиск через SQL с форматированным выводом
  4. Ограничение ответа: 4000 символов (лимит Telegram)

- `handle_voice()` — заглушка (голосовые сообщения не поддерживаются)
- `handle_photo()` — заглушка (изображения не поддерживаются)
- `handle_document()` — предлагает использовать /add для добавления файла как документа

**Почему так:**
- Единый метод `process_free_text` обрабатывает и поисковые, и непосиковые запросы
- Эвристика `_looks_like_search_request` определяет намерение пользователя без LLM (быстрее)
- Fallback при ошибке LLM обеспечивает бесперебойную работу
- Ограничение в 4000 символов соответствует лимиту Telegram на длину сообщения

## 🔄 Детальный поток выполнения

### Запуск бота:
1. `main.py` → `asyncio.run(main())`
2. Создание директорий `logs/` и `uploads/documents/`
3. `init_services()`:
   - `DocumentDatabase.initialize()` → создаёт таблицы БД (или JSON-фаллбек)
   - `LLMProcessor.__init__()` → настройка подключения к LM Studio
   - `DocumentService.__init__()` → связывает БД и LLM
4. `Application.builder().token().build()` → создание Telegram приложения
5. Сохранение сервисов в `app.bot_data`
6. `setup_handlers(app)` → регистрация всех обработчиков
7. `app.initialize()` → инициализация приложения
8. Запуск фоновой задачи `schedule_folder_import` (каждые 5 минут)
9. `app.start()` и `app.updater.start_polling()` → начало получения обновлений
10. Ожидание сигнала остановки (Ctrl+C)

### Получение сообщения:
1. Telegram → Bot API → python-telegram-bot → обработчик
2. Обработчик извлекает сервисы из `context.bot_data["document_service"]`
3. Вызывает соответствующий метод `DocumentService`
4. `DocumentService` выполняет логику (поиск в БД, генерация синонимов через LLM и т.д.)
5. Результат форматируется (HTML) и отправляется пользователю

### Пример: поиск с LLM при нехватке результатов SQL
1. Пользователь: `/find шпонка паз`
2. `find_command()` → `DocumentService.smart_search("шпонка паз")`
3. `DocumentDatabase.fulltext_search("шпонка паз")` → 0 результатов
4. `LLMProcessor.suggest_synonyms("шпонка паз")` → ["шпоночный паз", "шпонка", "паз под шпонку"]
5. Поиск по каждому синониму → найдены документы
6. Результаты объединяются, определяется best_match
7. Отправка списка + файла best_match

## 🛡️ Безопасность и отказоустойчивость

1. **Параметризованные запросы:** SQLAlchemy защищает от SQL-инъекций
2. **HTML-экранирование:** `_escape_html()` в commands.py предотвращает XSS
3. **Валидация файлов:** проверка расширения и размера перед сохранением
4. **Fallback JSON-хранилище:** при недоступности БД данные сохраняются в JSON-файлы
5. **Fallback без LLM:** при недоступности LM Studio бот использует базовый SQL-поиск
6. **Graceful shutdown:** корректное закрытие всех подключений при остановке
7. **Обработка таймаутов:** 120 секунд на запрос к LLM
8. **Лимиты:** 5 документов в контексте LLM, 5 файлов за раз, 10 документов на странице, 4000 символов в сообщении
9. **Уникальные имена файлов:** предотвращают перезапись и коллизии

## 🎯 Ключевые архитектурные решения и почему они приняты

1. **Асинхронность (asyncio):** Telegram Bot API требует обработки множества запросов одновременно. Асинхронный код позволяет не блокировать обработку одного запроса другим.

2. **SQLAlchemy ORM:** Абстрагирует работу с БД. Можно переключиться с SQLite на PostgreSQL, изменив только одну строку в `.env`.

3. **Паттерн Repository:** Изолирует логику доступа к данным от бизнес-логики. Упрощает тестирование и замену хранилища.

4. **Паттерн Service Layer:** Централизует бизнес-логику. Обработчики (handlers) занимаются только тем, как получить данные от пользователя и как их отобразить.

5. **RAG (Retrieval-Augmented Generation):** Комбинация поиска в БД + генерации LLM даёт более точные и релевантные ответы, чем каждый метод по отдельности.

6. **Fallback-механизмы:** Обеспечивают работу при частичной недоступности компонентов (БД, LLM). Критически важно для production-системы.

7. **ConversationHandler:** Стандартный механизм python-telegram-bot для многошаговых диалогов. Управляет состоянием автоматически.

8. **Единый обработчик callback-запросов:** Маршрутизация по префиксу callback_data упрощает архитектуру и позволяет легко добавлять новые типы кнопок.

## Актуализация: переход с Telegram на VK Callback API

Предыдущие разделы описывают исходную Telegram-версию. Точка входа проекта теперь использует HTTP Callback API сообщества VK; модули `handlers/commands.py`, `handlers/callbacks.py` и `handlers/messages.py` оставлены как неиспользуемый legacy-код. Бизнес-логика `DocumentService`, репозиторий, SQLAlchemy-модели, файловое хранилище и LLM переиспользуются.

### Что изменено

- `main.py` поднимает aiohttp-сервер, слушающий `HOST:PORT`, регистрирует callback-путь из `VK_CALLBACK_PATH` и `/health`, запускает фоновый импорт файлов и закрывает ресурсы при остановке.
- `handlers/vk_callback.py` проверяет секрет Callback API, возвращает код подтверждения, быстро подтверждает события и обрабатывает `message_new` в фоновой задаче.
- `services/vk_api.py` вызывает VK API и умеет отправлять сообщения и существующие файлы документов пользователям.
- `database.models.VKUser` и `DocumentDatabase.register_vk_user()` сохраняют первый контакт пользователя; новый пользователь получает приветствие со справкой один раз.
- Добавлены slash-команды и текстовые команды на русском: поиск, умный поиск, фильтр, список, карточка, скачивание, статистика, добавление карточки и смена статуса.
- Конфигурация callback-сервера задана через `HOST`, `PORT` и `VK_CALLBACK_PATH`; админ-список не используется.

### Настройка и запуск на сервере

1. Создать сообщество VK и включить сообщения сообщества.
2. Получить токен сообщества с правами на сообщения и документы, задать `VK_ACCESS_TOKEN`.
3. Задать `VK_CALLBACK_SECRET`, `VK_CONFIRMATION_CODE`, `VK_API_VERSION`, `HOST`, `PORT` и `VK_CALLBACK_PATH` в `.env`.
4. Запустить приложение на сервере. Оно слушает HTTP; TLS нужно завершить в Nginx/Caddy или другом reverse proxy.
5. Открыть для VK публичный HTTPS URL `https://домен/` (или другой callback path), передать в настройках сообщества секрет и версию API, пройти handshake кодом подтверждения и включить событие `message_new`.
6. Проверить `/health`, затем отправить тестовое сообщение со страницы/в диалог сообщества.

Callback-секрет обязателен при штатном запуске. Если меняется БД, новая таблица пользователей VK создаётся `Base.metadata.create_all`; существующие таблицы не переименовываются и не удаляются.

### Текущие ограничения и следующие работы

- VK-версия добавляет карточку текстовой командой, но пока не принимает вложенный файл как новый документ. Следующий шаг для полного равенства Telegram-мастеру — загрузка VK-вложения, проверка расширения/размера и пошаговое состояние добавления по `peer_id`.
- Telegram inline-кнопки/мастер на 8 шагов не переносятся автоматически. Для них нужно сделать VK-клавиатуры либо полностью оставить управление командами.
- Следует добавить дедупликацию повторных callback-событий по `event_id`; сервер подтверждает события сразу, поэтому временный сбой при последующей обработке может потребовать повторной доставки/защиты от повтора.
- Модель `User` и SQL-скрипт тестовых данных всё ещё содержат `telegram_id`; VK-пользователи сейчас хранятся отдельно. Если нужна единая авторизация/роли для нескольких каналов, следует перейти на общую таблицу платформенных аккаунтов и миграцию схемы.
- `python-telegram-bot` и старые Telegram handlers пока остаются в зависимостях/репозитории для переходного периода; активная точка запуска их не импортирует. После проверки VK в production можно удалить legacy-код, обновить зависимости и адаптировать старые тесты.
- Для доступа к изменению статуса и добавлению документов в этой версии используется общий режим без отдельной роли; при необходимости можно добавить ролевую модель и ограничения по пользователям, метрики и централизованный production supervisor.
- Секреты, HTTPS-домен, права токена, сетевые правила и фактическая конфигурация Callback API должны быть предоставлены/настроены владельцем сообщества и сервера; в репозитории они не хранятся.
